### 第 3 頁｜演練環境

這張是今天的演練環境，重點是中間那排字：**三條備份路徑，都落到叢集外的 Object Storage。**

左邊是叢集內。`dr-demo` 這個 namespace 是今天的受害者：一個 PostgreSQL，資料放在 Ceph 的 RBD 區塊儲存，是 RWO；另外還有一組 CephFS 的共享儲存，是 RWX。旁邊是 Velero server 和 node-agent，開了 CSI、用 kopia 上傳、啟用 Data Mover。還有一個 etcd 備份的 CronJob，目前是暫停的。

右邊是叢集外的一台備份機，IP `10.90.1.125`，上面跑 SeaweedFS，提供 S3 相容的 API，資料寫在一顆獨立的硬碟上。

三條路徑是這樣：Velero 把 Kubernetes 資源的 manifest 打包成 tar.gz，寫進 `velero/backups/`；node-agent 把 CSI 快照的內容用 kopia 上傳到 `velero/kopia/`，而且是去重、加密的；etcd 的 CronJob 把 snapshot 放進 `etcd-backups/`。

上面那行灰色的字很重要，我念一次：Ceph 跟叢集住在同一批節點上，CSI Snapshot 只存在 Ceph 裡；叢集整個消失，快照也一起消失。所以這座叢集的 Velero **一律開 snapshotMoveData**，把快照內容搬到叢集外。

【提醒】Velero UI 用的是 OTWLD 版本，網址 `velero.nexai.org.com`，掛在 admin-gateway 上。單元 3 會用到。

# 單元 1：Kubernetes 備份與復原概念（第 4–7 頁，7 分鐘）

### 第 4 頁｜單元 1 封面

單元 1：Kubernetes 備份與復原概念。

這個單元沒有實機操作，是觀念。我們先把「備份 Kubernetes」這句話拆開：到底要備份什麼、這些東西住在哪裡、要用什麼工具救。

### 第 5 頁｜Kubernetes Resource 與 Application Data

同一個應用，其實由兩種性質完全不同的東西組成。

左欄是 Kubernetes Resource：Deployment、Service、Secret、PVC 這些物件。它們是 YAML 或 JSON，每個只有幾 KB，住在 etcd 裡。通常可以重新產生，因為 Git 裡有 yaml。備份工具是 Velero 或 etcd snapshot。

右欄是 Application Data：PostgreSQL 裡的資料表、CephFS 上的檔案。它可能有幾百 GB，住在 PV 背後的儲存，也就是 Ceph。它**不能重新產生**，丟了就是丟了。備份工具是 Velero 的 Volume 備份，或者應用自己的 dump。

請看最下面這句話：etcd 裡只有「這裡應該有一個 10Gi 的 PVC」這個描述，PVC 裡面的內容不在 etcd。只備份 etcd 或只備份 YAML，救回來的是一個空殼。

一句話總結：**etcd 裡只有描述，沒有內容。**

單元 5 情境 1 會實際重現這件事：Pod Running、資料表也在，但訂單全部不見。

### 第 6 頁｜備份放在哪裡，決定能撐過哪種災難

這張表的橫軸是四種由小到大的災難：Pod 掛了、Namespace 被刪、Ceph 壞掉、整座叢集消失。縱軸是三種備份放的位置。

第一列，只有 CSI Snapshot，放在 Ceph 裡。Pod 掛了沒問題；namespace 被刪要看 deletionPolicy；Ceph 壞掉或叢集消失，快照就跟著沒了。

第二列，在 PVC 裡再放一份 dump。這很常見，但它只撐得過 Pod 掛掉。namespace 一刪，PVC 跟 dump 一起消失。

第三列，叢集外的 Object Storage。四種災難全部撐得住。

所以每一份備份都要能回答一個問題：**如果整座叢集，包含 Ceph，都不見了，這份備份還在嗎？**

下面三個理由說明為什麼選 S3。故障隔離：不同機器、不同磁碟，我們是 `10.90.1.125` 的 `/dev/sdb1`。共同語言：Velero、etcd 腳本、資料庫 dump 都講 S3 API，一套儲存收全部備份。可攜性：新叢集指向同一個 bucket，就看得到舊叢集的所有備份，這是單元 8 重建叢集的關鍵。

### 第 7 頁｜為什麼「有備份」不等於「一定能還原」

這張表是整門課的路線圖。

每一列是一個斷點，中間是症狀，右邊是今天在哪裡實測。

沒備份 Volume 資料：Pod Running、table 在，業務資料全空。排除了 Secret：`CreateContainerConfigError`。排除了 ConfigMap：卡在 ContainerCreating，事件是 FailedMount。目標叢集沒有同名的 StorageClass：PVC 永遠 Pending，還原變成 PartiallyFailed。快照前資料還在記憶體：檔案存在，但是 0 bytes。備份放在叢集裡：叢集一掛，備份也沒了。從來沒演練過還原：出事才發現少憑證、少步驟。

最下面這段是今天最重要的一句話之一：單元 5 的每一份備份，Velero 都顯示 **Completed、0 errors、0 warnings**。能證明備份有用的只有一件事：**定期實際還原，並用資料驗證。**

「備份成功」只證明 Velero 把你要它備份的東西寫進了 Object Storage。中間任何一環沒想到，就會變成一份 Completed 的備份，和一個救不回來的應用。

# 單元 2：建立外部 Backup Storage（第 8–11 頁，7 分鐘）

### 第 8 頁｜單元 2 封面

單元 2：建立外部 Backup Storage。

備份的第一條規則：**備份不能跟被備份的東西一起死掉。**

這個單元我們在叢集外的備份機上用 SeaweedFS 提供 S3，讓 Velero 寫進去，然後不透過 Velero，直接去 S3 確認資料真的寫出去了。

### 第 9 頁｜為什麼備份不能只放在叢集裡

一個很常見、看起來也很合理的設計，是在叢集裡開一個 Ceph RGW 或 MinIO 給 Velero 用。老實說，這座叢集真的有 `rook-ceph-retain-bucket` 這個 StorageClass，早期測試也這樣做過。

我們用這張表比較。誤刪 namespace，兩邊都救得回來。但 Ceph 故障的時候，叢集內的 RGW 是備份跟資料一起壞。etcd 壞掉、API Server 起不來，資料可能還在，但服務要靠叢集跑，叢集起不來就讀不到。整座叢集重灌、機房失火，就沒了。

最後一列最可怕：勒索軟體拿到 cluster-admin。叢集內的備份，一個 `kubectl delete` 就全部清掉。叢集外的，就要看 S3 帳號的權限怎麼設。

下面三個原則。不同的故障域：不同機器、不同磁碟，最好不同機房，也就是 3-2-1 原則。不同的權限域：cluster-admin 不應該能刪掉備份。不依賴被保護的系統：備份機自己要能獨立開機、登入、驗證。

### 第 10 頁｜Velero Credentials 與兩個關鍵 Secret

Velero 要連 S3，需要一組帳密。左邊是 credentials 檔的格式，就是標準的 AWS credentials 格式：access key 是 `velero-backup`，secret key 自己填。這個檔案**不要進版控**，權限設成 600。

右邊是兩個關鍵的 Secret，請大家一定要記得。

第一個叫 `cloud-credentials`。它是 `velero install --secret-file` 產生的，就是連 S3 的帳密，Velero server 和 node-agent 都會掛載它。

第二個叫 `velero-repo-credentials`，這個很多人不知道它存在。它是 kopia repository 的加密密碼，第一次用 Data Mover 的時候自動產生。PV 資料放在 S3 上，就是用這把密碼加密的。

請看下面紅框：新叢集如果產生了不同的 repo 密碼，**就讀不出舊叢集上傳的 PV 資料**。所以這個 Secret 要跟 S3 帳密一起，另外保存在叢集外。單元 8 重建叢集的時候，這會是關鍵的一步。

【提醒】輪替 S3 密碼的方式：`kubectl create secret ... --dry-run=client -o yaml | kubectl apply -f -`，然後重啟 velero Deployment 和 node-agent DaemonSet。有人問再講。

### 第 11 頁｜Available 只代表連得上，還要確認真的寫出去

Velero 裝好之後，第一個檢查是 `velero backup-location get`，看到 `default`、`Available`、`ReadWrite`。

但是 Available 只代表**連得上**，不代表**真的寫出去**。所以我們還要做第二件事：不透過 Velero，直接去 bucket 裡看。

左邊下半部就是這個做法。我們跑一個 `s3-check-pod`，它用 Velero 自己那組帳密，只做 `ls`。結果看到 `backups/dr-course-backup-01` 底下有一個 15508 bytes 的 tar.gz，這是資源的 manifest；`kopia/dr-demo` 底下總共約 37MB，這是 PV 資料經過壓縮、去重之後的大小。這就是不經過 Velero 的第二個證據來源。

右邊三個重點。Phase 是 Available：Velero 每分鐘驗證一次能不能存取 bucket。lastSyncedTime：Velero 會定期把 bucket 裡的備份清單同步回叢集，所以新叢集一接上，就看得到舊的備份。能讀出來才算數：用 `velero backup download` 下載 tar.gz，確認內容解得開。

最下面這個安全提醒請注意：備份 tar.gz 裡的 Secret 只是 base64，不是加密。**能讀 bucket 的人，就讀得到所有 Secret。**所以 bucket 的權限要收緊、要開 HTTPS、要用防火牆擋。

【提醒】SeaweedFS 安裝的細節、HTTP 切 HTTPS 的順序、BSL 常見錯誤，都在補充第 50–52 頁，主線不講。

# 單元 3：第一次 Backup（第 12–18 頁，14 分鐘）

### 第 12 頁｜單元 3 封面

單元 3：第一次 Backup，備份 Application。

我們要用 Velero UI 建立第一份備份。但這個單元的重點不在按鈕怎麼按，而是要學會回答一個問題：**這份備份，真的完成了嗎？**

### 第 13 頁｜受害者應用：dr-demo

先認識今天的受害者：`dr-demo`。

左邊這張表是它的組成。namespace 叫 `dr-demo`；帳密放在 Secret `postgres-secret`；一個 PostgreSQL 16 的 Deployment 加 Service；資料放在 RBD 的 PVC `postgres-data`，RWO；另外有一個 CephFS 的 PVC `shared-data`，RWX，由兩個測試 Pod `cephfs-test-1`、`-2` 共用。

為什麼同時放 RBD 和 CephFS？因為一個是區塊儲存、一個是檔案系統，兩種在備份上都要驗證。

右邊是準備步驟。`kubectl apply` 把應用建起來，等 rollout 完成。`write-postgres.sh` 寫入一筆測試資料 `DR-TEST-DB-001`。`check-data.sh` 檢查 PVC、資料庫、CephFS 檔案三大項，全部 PASS。最後 `baseline.sh` 留存一份叢集的基準紀錄，單元 7、8 也會用到。

請記住最下面這句：**備份前先跑一次 check-data.sh，這就是之後比對的基準。**還原之後，我們就是拿同一支腳本、同一筆資料來驗證。

【操作】如果時間允許，現場跑一次 `./dr/script/check-data.sh`，讓學員看到全部 PASS。

### 第 14 頁｜打開 Velero UI

接下來打開 Velero UI。網址是 `https://velero.nexai.org.com`，用課程帳號登入。DNS 還沒設定的同學，請在 hosts 把它指到 `10.90.1.90`。

右邊這張截圖是 Dashboard 首頁。上面四個數字：備份數、排程數、還原數、Storage Location 數。中間那排是：還沒排程的 namespace、接下來 24 小時的排程備份、最近 24 小時的備份。

左邊這張表是左側選單。最重要的是 Backups，今天這個單元用；Restores，單元 4 用；Schedules，單元 9；Storage Locations，可以順便確認 `default` 是 Available，呼應單元 2；Settings 可以看 Velero Server 和 Node Agent 的 log。

最下面這個框請大家記住：**UI 只是幫你建立 Velero 的 CR。**UI 掛了，排程備份照跑；反過來 Velero server 掛了，UI 按什麼都沒用。判斷成功與否，看的是 CR 的 status 和實際資料，不是 UI 上的顏色。

另外有一個安全提醒：這套 UI 的 ServiceAccount 綁的是 cluster-admin。能登入 UI 的人，就等同能在叢集裡還原任何東西。所以帳號要控管，HTTPRoute 也只掛在管理用的 admin-gateway 上。

【操作】現場打開 UI，帶學員看一圈左側選單。

### 第 15 頁｜建立備份：Backups → New

在 Backups 頁按 New，會打開一個叫「Create a new Backup」的精靈，上面五個步驟：Type、Info、Resources、Labels、Confirmation，一步一步按 Next step 往下。

這張表是每一步要填什麼，最右邊是它對應到 Backup CR 的哪個欄位。

Type 選 From Scratch。另一個選項 From a Schedule，是拿既有的排程當範本。

Info 是最重要的一步。Backup Name 填 `dr-demo-backup-01`；TTL 填 720 小時，也就是 30 天；Included Namespaces 填 `dr-demo`；Storage Location 選 `default`。

### 第 16 頁｜看備份進度：Backups 列表與詳細頁

送出之後，備份會經過上面這五個狀態：New、In Progress、Waiting For Plugin Operations、Finalizing、Completed。

其中 Waiting For Plugin Operations 最值得解釋。它代表 Kubernetes 資源已經備份完了，但 Data Mover 還在把 PV 資料上傳到 S3。這段通常最久，資料越大越久。

【提醒】截圖是 `daily-full-backup-20260916010019` 的詳細頁，不是 dr-demo-backup-01：Completed、29 秒、1484 / 1484 個物件。現場請打開自己的那份來講。

### 第 17 頁｜Volume Data Backup：三種方式

PV 資料的備份有三種方式。

第一種，只拍 CSI Snapshot，資料在 Ceph 裡。最快，但跟資料在同一個故障域，叢集消失就不在了。

第二種，CSI Snapshot 加 Data Mover，這是我們這座叢集用的。先拍一個時間點快照，再由 node-agent 把快照內容上傳到 S3 的 kopia。叢集消失，資料還在。

第三種，File System Backup，也是上傳到 kopia，但它是直接讀 Pod 掛載的目錄，**不是時間點快照**，一邊讀、應用可能一邊在寫。

Data Mover 的流程是這樣：Velero 建立 VolumeSnapshot，等 CSI 回報 ReadyToUse；node-agent 從快照建一個暫時的 PVC 並掛載起來，用 kopia 上傳到 S3，完成後回報上傳了多少 bytes；最後把暫時的 PVC 和快照刪掉。

下面是實測的結果。用 `kubectl get datauploads` 可以看到每一個 PVC 的上傳紀錄：`shared-data` 上傳了 45 bytes，`postgres-data` 上傳了 47876961 bytes，約 47.8MB。

`shared-data` 正好 45 bytes，就是 `dr-test.txt` 這個檔案的大小。**BYTES 是判斷資料有沒有真的被搬走最直接的數字。**如果這裡是 0，或根本沒有 DataUpload，那這份備份就沒有資料。

### 第 18 頁｜備份完成檢查清單：缺一不可

這是今天第一份檢查清單，八項，缺一不可。

一，Phase 是 Completed。二，Errors 等於 0，Warnings 每一個都看過。三，Items backed up 等於 Total items，我們是 19 / 19。四，Resource List 裡有 Deployment、Secret、Service、PVC。五，每一個 PVC 都出現在 Backup Volumes，而且 Result 是 succeeded。六，Moved data 的大小合理：47.8MB 和 45B。七，檔案真的在叢集外，這是單元 2 的方法。八，能還原，而且資料對，這是單元 4 要做的。

實測的 `dr-course-backup-01` 從 16:27:52 開始、16:29:30 完成，大約 98 秒，19 個物件全部備份，兩個 Volume 的 Data Movement 都 succeeded。

請看最下面這句話：**第 8 項是唯一真正能證明備份有用的一項。**單元 5 會示範，前面 1 到 7 全部打勾，第 8 項卻失敗的情況。

單元 4：第一次 Restore，把 Application 救回來。

### 第 20 頁｜兩種還原方式

還原有兩種方式。

建議的順序就是：先用第二種讓每個人安全練習，最後再示範一次第一種。

# 單元 5：Backup 的陷阱（第 24–28 頁，15 分鐘）

### 第 24 頁｜單元 5 封面

單元 5：Backup 的陷阱。

經過前面四個單元，大家應該覺得：備份 Completed、還原 Completed，就沒事了。這個單元就是要打破這個信心。

副標題：**每一份備份都顯示 Completed，卻沒有一份救得回可用的應用。**接下來的情境，全部都在真實叢集上實測重現。

### 第 25 頁｜Lab：一個 PostgreSQL，三種依賴

我們刻意設計了一個 lab 應用，放在 `dr-pitfall` 這個 namespace。它是一個 PostgreSQL，同時依賴三樣東西。

PVC：資料。三筆訂單 ORDER-1001 到 1003，只存在 PVC 裡。
Secret：帳密，用 `envFrom` 引用。
ConfigMap：初始化的 SQL，當成 volume 掛載，會產生一筆 SEED-0001 的種子資料。

設計成這樣的原因是：少了任何一個，還原後的症狀都不一樣。

然後我們做了四份備份。右邊是 `velero backup get` 的結果：`pitfall-full` 是完整的；`pitfall-no-data` 不含 Volume；`pitfall-no-secret` 排除 Secret；`pitfall-no-configmap` 排除 ConfigMap。

【停頓】

請大家看一下這四列。全部是 Completed、0 errors、0 warnings。**四份看起來一模一樣。**

Velero 只負責你要它備份的東西有沒有備份到，它不知道你的應用需要什麼。

接下來每一個情境，都是用 namespaceMapping 還原到獨立的 namespace，不影響來源。

### 第 26 頁｜情境 1：Resource 有了，Data 不存在

情境 1，用 `pitfall-no-data`，也就是沒有 Volume 資料的那份來還原。

看左邊這張表。Restore phase：Completed。Pod：Running 1/1。PVC：Bound。能連線、orders 這張 table 也存在。有資料嗎？有一筆……

然後最後一列：業務資料 ORDER-1001 到 1003，**全部消失**。

為什麼會這樣？右邊三步。第一步，備份裡沒有 Volume 資料，所以 PVC 動態佈建了一顆空磁碟。第二步，PostgreSQL 啟動時看到空目錄，就執行 initdb，還跑了 ConfigMap 裡的初始化 SQL。第三步，table 重建了、種子資料也塞回去了，看起來就是一個正常的資料庫。

這是整個單元最危險的情境，因為**每一項表面檢查都通過**。剩下的那一筆 SEED-0001，是種子資料，但它看起來就像真的資料。

所以最下面這句話：驗證腳本要查「**災難前才存在、不可能自動重生**」的資料，而不是查 table 在不在。這就是為什麼 `check-data.sh` 查的是 `DR-TEST-DB-001`。

【提問】你們公司現在的還原驗證，查的是「服務有沒有起來」，還是「某一筆舊資料在不在」？

### 第 27 頁｜情境 2、3：Secret 或 ConfigMap 遺失

情境 2 和 3，看上面這張表。

情境 2，備份排除了 Secret。這個 Secret 是用 `envFrom` 引用的，症狀是 `CreateContainerConfigError`，secret not found。注意，這時候 PVC 已經 Bound、資料也還原了，但容器根本啟動不了。

情境 3，備份排除了 ConfigMap。這個 ConfigMap 是當成 volume 掛載的，所以症狀不一樣：Pod 卡在 ContainerCreating，事件裡是 FailedMount。

左下是情境 2 的修復方式，很有代表性：**只從完整備份補還原缺的那一種資源。**`velero restore create`，`--from-backup pitfall-full`，`--include-resources secrets`，namespace mapping 到同一個目標。結果 kubelet 自動重試成功，不用重建 Pod，四筆訂單都在。

右邊兩個重點。

第一，**應用執行時不需要，不代表還原時可以不要。**這個 ConfigMap 只在第一次 initdb 的時候有用，資料庫跑起來之後根本不讀它。但 Pod spec 宣告要掛載它，kubelet 就會一直等。

第二，真實世界的變形：很多公司用 External Secrets 或 Vault，所以備份時排除 Secret。這沒問題，但前提是還原的時候 Vault 必須可用，而且 ExternalSecret 這個物件本身要在備份裡。

【提醒】情境 4（StorageClass 不存在）和情境 5（快照拍到 0 bytes）在補充第 60、61 頁。時間夠的話可以跳過去講，不夠就請學員課後看。

### 第 28 頁｜總整理：還原後的症狀 → 先懷疑什麼

這張表是還原除錯的速查表，建議大家拍下來。左邊是症狀，中間是第一個要懷疑的原因，右邊是怎麼確認。

Pod Running，但資料是空的或只有預設資料：懷疑沒備份 Volume，或 restorePVs 是 false。用 `describe --details` 看 Backup Volumes。

`CreateContainerConfigError`：env 引用的 Secret 或 ConfigMap 不存在。用 `kubectl describe pod`。

ContainerCreating 加 FailedMount：volume 掛載的 Secret、ConfigMap 或 PVC 不存在。看 Events。

PVC Pending 加 ProvisioningFailed：StorageClass 不存在。`kubectl get sc`。

卡在 WaitingForPluginOperations：Data Mover 還在下載，或 PVC 沒辦法 Bound。看 `datadownloads`。

檔案在但 0 bytes：快照前資料還沒落盤，要加 pre-backup hook。

連不到其他 namespace 的服務：NetworkPolicy 或 namespace label 沒回來。`kubectl get ns --show-labels`。

【提醒】課後清理：刪除 `dr-pitfall` 相關的 namespace、`rook-ceph-block-legacy` StorageClass，並用 `velero backup delete` 刪掉 pitfall 系列備份。

# 單元 6：建立 etcd 備份與還原策略（第 29–32 頁，9 分鐘）

### 第 29 頁｜單元 6 封面

單元 6：建立 etcd 備份與還原策略。

到這裡為止，我們都在處理應用。現在往下一層，到 control plane。

一句話分清楚：**Velero 保護的是應用；etcd snapshot 保護的是叢集本身。**

這個單元的 yaml 跟線上 `etcd-backup` namespace 裡的物件完全一致，線上目前是 suspend，由我決定上課時要不要操作。

### 第 30 頁｜etcd Snapshot：只有一半

左邊是拍 etcd snapshot 的指令。`etcdctl snapshot save`，連到本機的 2379，帶上 etcd 的 CA、憑證和私鑰。拍完之後用 `etcdutl snapshot status` 確認內容。

這是線上操作，不用停 etcd。注意工具的分工：save 用 `etcdctl`；status 和 restore 用 `etcdutl`，因為 etcd 3.6 已經把 restore 從 etcdctl 移除了。

但是標題說：**snapshot 只有一半。**另一半在右邊這張表，這些檔案不在 snapshot 裡，要另外備份。

`encryption-config.yaml`，少了它，讀不出任何 Secret，因為我們這座叢集有開 Secret 靜態加密。`pki` 裡的 `ca.*` 和 `sa.*`，少了它，所有 kubeconfig 和 token 全部失效。`pki/etcd/*`，少了它，etcd 成員之間的 mTLS 建不起來。`manifests/*.yaml`，少了它，你不知道 control plane 原本的啟動參數。

這些檔案由 `backup-control-plane-files.sh` 負責備份。

【提醒】線上 CronJob 把「拍 snapshot」和「上傳」拆成兩個容器，因為官方 etcd image 是 distroless，沒有 shell。snapshot 暫存在 Pod 的 emptyDir，Pod 結束就刪除，不在節點上留副本，因為 snapshot 裡有所有 Secret 的密文。

### 第 31 頁｜etcd Backup 與 Velero Backup 的差異

這張表逐項比較兩種備份。

備份什麼：etcd snapshot 是 etcd 裡的全部 key；Velero 是選定範圍的資源加上 PV 資料。
PV 資料：etcd snapshot 沒有；Velero 有，靠 CSI Snapshot 加 Data Mover。
粒度：etcd snapshot 是全有或全無；Velero 可以按 namespace、資源種類、label 選。
一致性：etcd snapshot 是整座叢集同一個時間點；Velero 是逐一讀取，不是原子性的。
還原影響：etcd snapshot 是整座叢集回到過去，**所有租戶都受影響**；Velero 只影響被還原的範圍。
需要叢集活著嗎：etcd snapshot 不需要；Velero 需要 API Server。
能還原到別的叢集嗎：etcd snapshot 不建議；Velero 可以，這是它的設計目標之一。

最下面一句話：**它們互補，不是二選一。**

### 第 32 頁｜什麼情況用哪一種 Restore

我們用七個情境來練習判斷。

誤刪 `dr-demo` namespace：用 Velero，只救一個 namespace，不影響其他團隊。

資料被錯誤的 migration 寫壞：用 Velero，而且要 restorePVs，因為 etcd 裡根本沒有資料庫的資料。

3 台 etcd 中 1 台硬碟壞掉：**兩個都不用**，替換成員就好，其餘 2 台還有 quorum。

3 台 etcd 資料全部損壞：用 etcd snapshot。API Server 起不來，Velero 無能為力。

有人下了 `kubectl delete crd --all`：etcd snapshot，但前提是你能接受整座叢集回到過去。因為刪除 CRD 會連帶刪除所有對應的 CR。

Kubernetes 升級失敗想退回：用升級前拍的 etcd snapshot，整座叢集要一致地回到升級前。

整座叢集或機房消失：重建加 Velero。新機器、新 IP，舊的 snapshot 不適用。

判斷流程可以這樣記：先問 **API Server 能不能用**。不能用，再問 etcd 還有沒有多數成員健康：有，就替換故障成員；沒有，才用 snapshot 還原。能用，就看影響範圍：一個應用用 Velero；大量叢集資源被刪，要看能不能接受整座叢集回到過去。整座叢集不見，走單元 8。

# 單元 7：Control Plane Disaster（第 33–35 頁，6 分鐘）

### 第 33 頁｜單元 7 封面

單元 7：Control Plane Disaster，etcd 還原。

主題是：API Server 起不來的時候，怎麼從 snapshot 把叢集救回來。

先強調一次，這個單元是 runbook，**不在這座共用叢集上執行**。etcd 一還原，整座叢集，包含其他團隊的 vui、cattle、rook-ceph，全部回到 snapshot 的時間點。要練習請在專用的 lab 叢集，例如一台單機的 kubeadm VM。

### 第 34 頁｜API Server 異常時看到的現象

control plane 出事的時候長什麼樣子？這張表比較兩種情況：etcd 停止或失去 quorum，以及 etcd 的資料被清空。

`kubectl get nodes`：前者是 request timed out 或 connection refused；後者是 No resources found 或 Forbidden，因為資料不見了。

kube-apiserver：前者反覆重啟，因為 liveness 失敗；後者正常運作，還會開始重建預設物件。

現有的 Pod：兩種都會繼續運作，後者只能撐一段時間。

對外服務：前者大多仍然連得到；後者會逐漸異常。

新部署、擴縮、自我修復：兩種都全部停擺。

判讀重點是：**服務還在，但 kubectl 什麼都做不了**，這是 control plane 災難的特徵，跟應用掛掉完全不同。

下面兩行指令是第一步。第一步永遠是**上節點看，不靠 kubectl**：用 `crictl ps -a` 看 etcd 和 kube-apiserver 的容器狀態，用 `journalctl -u kubelet` 看 kubelet 最近十分鐘的 log。

### 第 35 頁｜從 Snapshot 還原：每一步 3 台都完成才往下

還原分五步，標題是規則：**每一步 3 台都完成，才往下一步。**

第一步，停止。把 apiserver、controller-manager、scheduler、etcd 的 manifest 從 `/etc/kubernetes/manifests` 移走。static Pod 是 kubelet 監看這個目錄產生的，manifest 移走就等於停止。

第二步，重建。舊的資料目錄保留下來，用 mv 不要 rm，然後 3 台從**同一份** snapshot restore。

第三步，啟動 etcd。確認 3 台都健康、而且只有一個 leader。

第四步，啟動 control plane。把 manifest 移回去，重啟 kubelet。

第五步，驗證。API、Secret 能不能解密、時間點對不對、應用正不正常。

下面是 k8s01 的 restore 指令：`--name` 是自己的名字；`--initial-cluster` 列出三台成員和它們的 2380 peer 位址；`--initial-advertise-peer-urls` 是自己的位址；`--initial-cluster-token` 用一個新的 token；`--data-dir` 指到 `/var/lib/etcd`。

最下面這句是細節但很重要：**3 台用同一個 token，而且要跟原本的叢集不同**，這樣才不會跟殘留的舊成員互相加入。

【提醒】`restore-etcd-member.sh` 把 stop、restore、start-etcd、start-cp 包成子指令，預設 dry-run，加 `--execute` 才真的執行。還原前的 12 項安全確認和還原後驗證在補充第 68–71 頁。

單元 8：Cluster Disaster，整個叢集消失。

### 第 37 頁｜叢集消失後，什麼還在、什麼沒了

叢集可能怎麼消失？機房停電加上儲存陣列損壞、虛擬化平台誤刪整組 VM、勒索軟體、升級失敗到無法回復。

應用的 PV 資料，原本在 Ceph，也就是節點磁碟，沒了，只剩 snapshotMoveData 搬出去的那一份。
沒搬出去的 CSI Snapshot，在 Ceph，跟著沒了。
etcd snapshot 和 Velero 備份，在 S3，還在。
manifest、Helm values，在 Git，還在。

倒數第二列是最容易漏掉的：`velero-repo-credentials`，它是叢集內的 Secret，**沒了。除非另外保存，否則讀不出 PV 資料。**這就是單元 2 埋的伏筆。

最後一列，S3 credentials 和 TLS 憑證，也是叢集內的 Secret，還在不在要看你有沒有另外保存。

### 第 38 頁｜重建順序

左邊是重建的順序，從 0 到 9。每一步都有檢查點，通過才往下。

第 0 步，宣告災難、啟動 DR 流程，把「DR 保險箱」拿出來。
第 1 步，節點的 OS 加 containerd。
第 2 步，kubeadm init、join；kube-vip 的 VIP、gpu01 的 taint。
第 3 步，裝 Cilium CNI，節點才會變 Ready。
第 4 步，Rook-Ceph。**StorageClass 名稱一定要跟舊叢集相同**，不然就是單元 5 的情境 4。還要裝 snapshot-controller 和 VolumeSnapshotClass。
第 5 步，Gateway API：LB 的 IP Pool、Gateway、TLS Secret。
第 6 步，**先還原 `velero-repo-credentials`，再 velero install**，指向同一個 bucket。順序不能反。
第 7 步，確認舊的備份同步出現。
第 8 步，分批用 Velero Restore 應用。
第 9 步，驗證資料、切換 DNS、宣告恢復。

### 第 39 頁｜單元 9 封面

最後一個單元：每日備份與 Restore 驗證機制。

**備份不是一個動作，是一個制度：每天跑、會叫人、定期證明能還原。**

### 第 40 頁｜這座叢集的現況：兩個沒人發現的問題

先講一個真實的故事。撰寫這個單元的時候，我們檢查了線上那個 `daily-full-backup` 排程，發現了兩個問題。

問題 1，左邊：**連續 5 天沒有備份，沒有任何告警。**9 月 16 號有一份，然後 17 到 21 號完全沒有任何紀錄，22 號才又出現。

為什麼沒人發現？因為沒有「失敗」。備份根本沒被產生，所以也沒有失敗可以通知。**只做失敗通知的監控，在這種情況下完全無效。**原因沒有查明，同一段時間 Velero Pod 被重建過好幾次，但重點是五天內沒有任何人知道。

問題 2，右邊：**每日備份還原不回 PV 資料。**我們拿每日備份做還原測試，結果 PartiallyFailed，2 個錯誤，訊息是 `multiple DataUpload result cms found`。

原因是這個排程沒有排除 `velero` 這個 namespace。所以備份裡夾帶了其他備份的 DataUpload 物件，同一個 PVC 出現 3 筆紀錄，還原時 Velero 不知道該用哪一筆。

對照組：用只備份 dr-demo 的 `dr-course-backup-01` 做同一套還原流程，完全正常，4 項 PASS，耗時 1 分鐘。

【停頓】

請看最下面這句：這三份每日備份，**每一份都顯示 Completed、0 errors、0 warnings。**

【提醒】修正方式（排除 velero 等 namespace）在補充第 76 頁，yaml 在 `dr/09-daily-backup-verification/velero/schedule-daily-full.yaml`，目前沒有套用。

### 第 41 頁｜可靠的每日備份需要三層

那要怎麼做？可靠的每日備份需要三層。

第一層，產生：Schedule。它回答「有沒有在跑？」每天 01:00 UTC 產生一份 Backup。

第二層，檢查：`backup-check`。每天 03:00 跑，回答「備份存在嗎、夠新嗎、成功嗎？」

第三層，驗證：`restore-test`。每週一 04:00 跑，回答「真的能還原、資料對嗎？」

左下是 backup-check 的五個檢查項目：BSL 是 Available；Schedule 是 Enabled 而且沒有被 pause；最新一份 Completed 的備份距今不超過 26 小時；最新成功的備份 errors 等於 0；最新一次不是 Failed 或 PartiallyFailed。

其中「26 小時」這一項，就抓得到問題 1。

右下是一個很重要的觀念：**成功也要通知。**每天固定收到一則成功的訊息，哪一天沒收到，那就是訊號。為什麼？因為如果只在失敗時通知，檢查程式自己沒跑，就會被當成一切正常。這叫 dead man's switch，也可以再接 Healthchecks.io 或 Uptime Kuma 做心跳監控。

Velero 本身沒有內建通知，所以我們用 CronJob 跑 `backup-check.sh`，呼叫 webhook，Slack、Mattermost、Google Chat 都可以接。

【提問】backup-check 抓得到問題 2 嗎？
參考答案：抓不到。那份備份的每一個狀態欄位都是完美的，只有真的還原才看得出來。這就是為什麼一定要有第三層。

### 第 42 頁｜RPO / RTO：用演練證明的數字

最後講兩個數字。

RPO，最多能遺失多久的資料，由備份頻率決定。每日備份，最差就是 24 小時。但是像問題 1 那樣斷掉 5 天，實際的 RPO 就是 5 天。

RTO，多久要恢復服務，由還原流程決定：偵測、決策、還原、驗證、切換，全部加起來。

可以想像一條時間軸：最後一次成功備份到災難發生之間，是資料遺失，就是 RPO；災難發生到服務恢復之間，是停機，就是 RTO。

下面這張表是今天課程的實測數字。dr-demo 還原到新 namespace，約 48MB，Restore 55 秒，含驗證約 1 分鐘。dr-demo 備份 98 秒。全叢集每日備份 1687 個物件，約 6 分鐘。etcd 還原和整座叢集重建沒有實測，重建通常以小時計。

這些數字可以當作 RTO 的參考下限。真實的災難還要加上發現問題、做決策、找人的時間。

## 補充 · 單元 1

### 第 47 頁｜etcd 保存什麼，不保存什麼

etcd 是 Kubernetes 唯一的資料庫，只有 API Server 直接讀寫它。所有 `kubectl get` 看得到的東西，最後都是 etcd 裡的一筆 key/value。

左邊是 etcd 裡有的：所有 namespace、資源、CRD 物件；RBAC、Node 物件、Lease、Event；連 Velero 的 Backup CR 也在。例如 `/registry/deployments/dr-demo/postgres` 就是 dr-demo 那個 Deployment 的 key。

右邊是 etcd 裡沒有的：容器 image；PV 裡的資料和節點上的檔案；etcd 自己的憑證，在 `/etc/kubernetes/pki`；還有 Secret 靜態加密的金鑰 `encryption-config.yaml`。

其中加密金鑰最容易被忽略。我們這座叢集有開 Secret 靜態加密，只有 snapshot、沒有 `encryption-config.yaml`，還原之後 API Server 讀不出任何 Secret。

### 第 48 頁｜PVC、PV 與實際資料

右邊這三個方塊，由上往下是一條鏈。

PersistentVolumeClaim 住在 etcd，內容是「我要 10Gi、RWO、rook-ceph-block」。PersistentVolume 也住在 etcd，內容是「我綁到 Ceph 上的哪一顆 image」。只有最下面的 RBD image 或 CephFS subvolume，住在 Ceph，是應用真正寫入的資料。

左邊這張表是 dr-demo 的兩種 StorageClass：`rook-ceph-block` 是 RBD、RWO，`postgres-data` 約 47.9MB；`rook-cephfs` 是 CephFS、RWX，`shared-data` 是 45 bytes。兩種都用 CSI Snapshot 加 Data Mover 備份，快照類別分別是 `csi-rbdplugin-snapclass` 和 `csi-cephfsplugin-snapclass`。

最下面的警告：reclaimPolicy 是 Delete。刪掉 PVC 或整個 namespace，Ceph 上的資料會立刻一起刪除，**沒有資源回收筒**。

### 第 49 頁｜Velero 與 etcd Backup 各解決什麼問題

左邊是 Velero。它跑在叢集裡，透過 API Server 逐一重建資源。適合誤刪一個 namespace 或應用、應用資料被寫壞時還原 PV 資料、把應用搬到另一座叢集。但 etcd 損壞、API Server 起不來的時候它無能為力，也不擅長整座叢集精確的時間點。

右邊是 etcd snapshot，整個資料庫的完整、一致的複本。etcd 損壞或失去 quorum 時，它是唯一解；大量叢集層級資源被刪時也適合。但只想救一個 namespace 的話它太粗；它救不回 PV 裡的資料；也不建議還原到別的叢集。

兩者互補，單元 6 會再用決策表整理。

## 補充 · 單元 2

### 第 50 頁｜SeaweedFS 備份機：五個檢查點

我們用 SeaweedFS 的 `weed mini`，也就是單機全功能模式，跑在叢集外的一台 Ubuntu 26.04 備份機 `10.90.1.125`，資料放在獨立的第二顆硬碟。這裡只列五個關鍵檢查點。

一，獨立硬碟掛在 `/backup`，用 `df -h /backup` 確認是 `/dev/sdb1`，確保資料沒有寫到系統碟。

二，systemd 設定 `RequiresMountsFor`，硬碟沒掛上，服務就不會啟動。避免資料默默寫進根目錄。

三，兩組 S3 帳號：`seaweed-admin` 負責管理；`velero-backup` 只能存取 velero bucket。權限分離，Velero 不能建立或刪除 bucket。

四，由管理者先建立 bucket，用 admin 帳號執行 `aws s3 mb s3://velero`。用 velero 帳號執行 mb 會得到 AccessDenied，這是預期的。

五，reboot 測試，重開機後 `systemctl is-active seaweedfs`。備份機自己也要能在災難之後恢復。

完整的安裝步驟在 `dr/seaweedfs/README.md`。etcd 備份用的 `etcd-backups` bucket，建議用另一組帳號。

### 第 51 頁｜建立 Backup Storage Location

左邊是這座叢集實際的安裝參數，腳本是 `02-backup-storage/velero/install-velero.sh`，單元 8 重建叢集時會重用。

provider 是 aws；plugin 是 `velero-plugin-for-aws:v1.14.2`；bucket 是 velero；`--secret-file` 指到 credentials 檔；BSL 的設定是 region、`s3ForcePathStyle` 和 s3Url；然後 `--features=EnableCSI`、`--use-node-agent`、`--uploader-type kopia`。自建的 S3 一律要加 `s3ForcePathStyle`。

右邊是 HTTP 切換到 HTTPS 的正確順序。線上目前是 HTTP 直連 8333，備份機上已經建好 Nginx 加 TLS 和防火牆規則。順序是：一，apply `bsl-https.yaml`，填入 caCert；二，確認 `velero backup-location get` 仍然是 Available；三，跑一次小備份，確認寫得進去；四，最後才在備份機上 `ufw deny 8333/tcp`。

如果先開防火牆、BSL 還沒切換，Velero 會立刻變成 Unavailable，所有備份失敗。

### 第 52 頁｜常見錯誤

這六個錯誤都跟 BSL 有關。

BSL Unavailable，log 裡有 AccessDenied：credentials 錯，或沒有 bucket 權限。用 `s3-check-pod` 拿同一組帳密測 `ls`。
NoSuchBucket：bucket 沒有事先建立。用 `seaweed-admin` 執行 `aws s3 mb`。
SignatureDoesNotMatch：reverse proxy 改寫了 Host，或 URL 不一致。Nginx 要 `proxy_set_header Host`，兩邊 URL 要一致。
`x509: unknown authority`：自簽憑證，Velero 不信任。在 BSL 的 `objectStorage.caCert` 填 Root CA。
`dial tcp …:8333: i/o timeout`：防火牆擋住，或 BSL 還是指向 8333。照上一頁的切換順序。
virtual-host 網址錯誤：忘記 `s3ForcePathStyle`。

排錯原則是縮小範圍：先用 `s3-check-pod` 確認同一組帳密能不能 ls，就能分辨是 S3 端的問題，還是 Velero 設定的問題。

### 第 55 頁｜Label Selector 的陷阱

這是 9 月 23 日對 dr-demo 實測的結果。

結論：要用 selector，先規定所有資源都貼 `app.kubernetes.io/instance`；不然，用 namespace 當邊界最安全。

### 第 60 頁｜情境 4：StorageClass 不存在

真實的情境是：舊叢集的 StorageClass 叫 `ceph-block-ssd`，新叢集改了名字，但備份裡的 PVC 還寫著舊名字。

我們在同一座叢集重現：建立一個 `rook-ceph-block-legacy` StorageClass，用它建 PVC、備份，然後刪掉這個 StorageClass，再還原。

左上是結果：`legacy-data` 永遠 Pending，`postgres-data` 是 Bound。Restore 是 PartiallyFailed，錯誤訊息是 storageclass not found。已經 Bound 的 PVC 不受影響，因為 PV 不依賴 StorageClass 物件存在。

注意中間這句：沒有加 `--item-operation-timeout`，這個 Restore 會卡在 WaitingForPluginOperations，**最多 4 小時才失敗**。

右邊是解法：一個 `change-storage-class` ConfigMap，放在 velero namespace，貼兩個 label，data 寫「舊名字：新名字」，也就是 `rook-ceph-block-legacy: rook-ceph-block`。套用之後再還原，就是 Completed，PVC 被改寫成新的 StorageClass。

但要注意，這是全域設定，對之後所有的 Restore 都生效，所以要納入版本控管，用完移除。

那檔案的內容呢？這就帶出下一個情境。

### 第 61 頁｜情境 5：快照拍到還沒寫進磁碟的資料

這不是原本設計的情境，是實測時真的踩到的問題。

右上是現象：還原後的 `legacy.txt` 是 **0 bytes**；來源明明是 56 bytes。

右下是時間軸。08:33:01 寫入 `legacy.txt`，這時候資料在 page cache，也就是記憶體裡。08:33:16 備份開始，幾秒後拍 CSI 快照。ext4 的 journal 每 5 秒提交一次，所以「檔案存在」這件事已經落盤了；但檔案的內容最多要 30 秒才寫回磁碟。所以快照拍到的是一個存在、但 0 bytes 的檔案。

原因是：CSI Snapshot 拍的是區塊裝置，不是應用程式的記憶體。這叫 **crash-consistent**，跟突然拔電一樣。

PostgreSQL 的資料為什麼沒事？因為資料庫每次 COMMIT 都會 fsync。一般應用寫檔通常不會。

左邊這張表是四種做法：什麼都不做，是 crash-consistent；加 sync hook，已寫入的資料都會落盤；fsfreeze 的 pre 和 post hook，快照期間凍結檔案系統；pg_dump 或 CHECKPOINT，是 application-consistent。

我們做了 A/B 實驗：沒有 hook 的檔案 0 bytes，加了 sync hook 的是 48 bytes，內容完整。Hook 可以寫在 Backup 的 `spec.hooks`，也可以寫在 Pod template 的 annotation。

### 第 62 頁｜Namespace 與資源的跨界依賴

Velero 以 namespace 為邊界備份，但應用的依賴常常跨出這個邊界。這張表的例子都來自實戰部署工作坊。

跨 namespace 連線：cloudbeaver 連 flarum、planka、peertube 的資料庫。只還原 cloudbeaver，它回來了，對面的 DB 不在。

共用 Gateway：所有 HTTPRoute 都掛在 default 的 `dev-gateway`。HTTPRoute 還原了，但 Accepted 是 False。

Namespace label 加 NetworkPolicy：cloudbeaver 用 namespaceSelector。label 沒回來，流量就被擋。這裡 Cilium 有一個已知陷阱：Pod 建立時就計算身分，所以 namespace label 要比 Pod 先存在。

Cluster-scoped 資源：StorageClass、ClusterRole、CRD，預設不會跟著 namespace 備份。

CRD 與 Operator：例如 Rook 的 CephCluster，CRD 在但 Operator 沒跑，就沒人處理。

TLS 憑證 Secret：`default/gateway-tls` 在別的 namespace，不會跟著備份。

做法是：為每個應用寫一張依賴清單，還原演練時逐項確認；或者把有依賴關係的 namespace 放進同一份備份。

### 第 64 頁｜etcd 在 Kubernetes 中的角色

左邊這三層：kubectl、Velero、各種 Controller，所有元件都經過 API Server；kube-apiserver 是唯一直接讀寫 etcd 的元件；etcd 是強一致的 key/value 資料庫，用 Raft 演算法。

右邊三個重點。

etcd 掛了：kubectl 全部失敗、Controller 停擺；但已經在跑的容器不會馬上停，因為 kubelet 會繼續維持現有的 Pod。

服務還在，什麼都不能改：這是 control plane 災難的典型特徵。

3 個成員容忍 1 個故障：需要多數，也就是 2 票；2 個同時掛掉就失去 quorum。

### 第 65 頁｜這座叢集的 etcd

這些值是從 `etcd-k8s01` 的 Pod yaml 查到的。

拓樸是 stacked，k8s01 到 03 各跑一個 static Pod，所以還原時 3 台都要處理。版本 etcd 3.6.6，還原時要用同版本的 etcdctl 和 etcdutl。資料目錄 `/var/lib/etcd`，還原會產生新的資料目錄。憑證在 `/etc/kubernetes/pki/etcd/`，連線要 mTLS，而且憑證不在 snapshot 裡。static Pod 的 manifest 是 `/etc/kubernetes/manifests/etcd.yaml`，移走它就停止 etcd。Secret 加密金鑰 `encryption-config.yaml`，snapshot 裡是密文，金鑰必須另外備份。VIP 是 kube-vip 的 `10.90.1.80`，還原期間 API 不通，VIP 可能會漂移。

【提醒】撰寫教材時自動化環境不允許直接對 etcd 執行指令，所以沒有附 `member list` 的實測輸出。請講師課前自己跑一次並記錄 DB 大小，作為估算備份檔大小與還原時間的依據。

### 第 66 頁｜保存位置與備份頻率

左邊是存放位置的評價。control-plane 本機：節點壞了一起沒。叢集內的 PVC：要叢集活著才能讀。叢集外 S3 的 `etcd-backups/<node>/`：本課程的做法。再複製到異地或離線媒體：防勒索、防機房災難。

右邊是頻率，由 RPO 決定。設定很少變動的叢集，每日、保留 30 天。經常部署的共用叢集，每 6 小時到每日，重大變更前手動拍一次。完全由 GitOps 管理的叢集，每日、保留 14 天。snapshot 通常只有數十到數百 MB，寧可多留。

最下面這句最重要：**監控「最新一份備份的時間」比保留天數更重要。**如果上傳一直失敗、清理一直成功，最後一份好的備份也會被刪掉。我們線上的腳本 `RETENTION_DAYS=30`，而且清理是在上傳成功之後才跑，就是為了避免這件事。

### 第 67 頁｜講師操作：啟用並驗證 etcd 備份

這是啟用 etcd 備份的五個步驟。

一，`kubectl apply --dry-run=server`，確認 yaml 跟線上一致。二，用 `create job --from=cronjob` 手動觸發一次，不用改 suspend。三，看 etcd-snapshot、etcd-snapshot-status、upload 三個容器的 log。四，用 aws CLI 直接 ls `etcd-backups/k8s01/`，確認檔案真的在叢集外。五，驗證 snapshot 能用：在任何一台 Linux 上下載，`etcdutl snapshot restore` 到一個暫存目錄，能解開就代表檔案完整，完全不碰線上 etcd。

另外還有第六步：在每台 control-plane 上用 root 執行 `backup-control-plane-files.sh`，備份 snapshot 以外的必需檔案。

最下面的提醒：這些步驟會改變線上狀態，因為會寫入 S3。要解除 suspend 讓它每天自動跑，要由講師在課堂上確認後再做。

### 第 68 頁｜情境與範圍

單元 7 處理的情境是：3 台 control-plane 的 etcd 資料同時損壞，etcd 失去 quorum，API Server 無法運作。目標是用單元 6 的 snapshot 和 control-plane 檔案，把叢集重建回 snapshot 的時間點。

### 第 69 頁｜還原前的 12 項安全確認

etcd 還原是整座叢集風險最高的操作。正式環境執行前，這 12 項要逐項確認並留下紀錄。

一，真的需要還原嗎？只壞 1 台就替換成員。二，取得核准，通知所有租戶。三，選定損壞前的最後一份 snapshot。四，3 台用同一個檔案，比對 sha256。五，etcdutl 的版本等於叢集 etcd 的版本。六，`encryption-config.yaml` 跟 snapshot 是同一時期的。七，`/etc/kubernetes/pki` 完整。八，保留損壞的資料目錄，用 mv，不要 rm。九，有節點的 console 或 BMC 存取權。十，規劃還原後的 PV 對帳和 GitOps 同步。十一，暫停 CI/CD、Fleet、Velero Schedule。十二，兩人作業，一人執行、一人對照。

特別講兩項。第六項：金鑰如果在 snapshot 之後輪替過，還原後所有 Secret 都無法解密。第九項：還原過程中 API 不通，kube-vip 的 VIP 也可能漂移，SSH 或 console 是唯一的入口。

### 第 70 頁｜還原後的驗證

還原完成後，分四格驗證。

API Server：`/readyz?verbose` 和 `kubectl get nodes`。

Secret 解密，這是最容易忽略的一項：讀一個 Secret 出來 base64 decode，例如 dr-demo 的 `postgres-secret`。如果看到 `failed to decrypt`，就是金鑰跟 snapshot 對不上。

時間點正確：`kubectl get ns after-snapshot` 應該是 NotFound，因為它是 snapshot 之後才建的。再用 `baseline.sh` 跟災難前的紀錄比對。

應用：`check-data.sh dr-demo`。

最下面這句很重要：**etcd 還原不會動到 PV 資料。資源回到過去，資料停在現在。**snapshot 之後寫進 PostgreSQL 的資料，仍然在 Ceph 裡。所以 etcd 還原後，常常出現資源和資料不同時間點的混合狀態。

### 第 71 頁｜還原後的副作用與清理

這張表是還原後常見的副作用。

孤兒 PV：snapshot 之後建立的 PVC，Ceph 有 image，但 etcd 裡沒有 PV。比對 `rbd ls` 和 `kubectl get pv`，確認後清理。

斷掉的 PV：snapshot 之後刪除的 PVC，etcd 裡又出現了 PV，但 Ceph 上已經沒有。刪除 PVC 和 PV，由應用或 Velero 補回。

Deployment 版本回退：snapshot 之後的部署消失了。用 GitOps 重新同步，或重跑 CI/CD。

Velero 備份清單：snapshot 之後的 Backup CR 消失了。不用擔心，Velero 會從 bucket 自動同步回來。

Lease 和 leader election 混亂：各元件的 lease 回到過去，通常幾分鐘內恢復，必要時重啟元件。

最後，記得恢復第 69 頁暫停的自動化，並做事後檢討：損壞原因、實際 RTO、snapshot 跟事件的時間差也就是實際 RPO、runbook 哪裡不清楚，然後更新文件。

## 補充 · 單元 8

### 第 72 頁｜DR 保險箱：災難前就必須存在叢集外

這份清單要在災難**之前**就準備好，而且放在叢集外、離線也拿得到。

一，`velero-repo-credentials`，kopia repository 的密碼。二，Velero 的 S3 credentials。三，etcd 備份的 S3 credentials。四，TLS 憑證與私鑰、Root CA。五，應用的外部相依資訊：外部 DB、SMTP、OAuth secret。六，這個 repo：manifest、Helm values、`install-velero.sh`。七，最新的 `baseline.sh` 輸出。八，這份 runbook 的紙本或離線版本。

`velero-repo-credentials` 的匯出方式：`kubectl get secret` 取出 yaml，去掉 uid、resourceVersion、creationTimestamp 再保存。

練習題：你們公司現在，這八項有幾項是真的存在叢集外的？

### 第 73 頁｜重新連接 Backup Storage：順序很重要

新叢集裝好基礎元件之後，要重新接上舊的備份。順序很重要。

第一步，先放回**舊的** repo 密碼，也就是從 DR 保險箱拿出 `velero-repo-credentials`，建立 velero namespace 然後 apply。

第二步，安裝 Velero，指向同一個 bucket，用 `install-velero.sh`。

第三步，先把 BSL 設成 ReadOnly，避免誤刪或誤寫舊的備份。

第四步，`velero backup get`，確認舊的備份同步出現。

紅框是這一頁的重點：沒有先放 `velero-repo-credentials`，Velero 會產生一組新的密碼。結果是資源還原成功、PV 資料失敗，又是一個「看起來大致成功」的陷阱。這就是單元 2 那個 Secret 的伏筆。

全部還原完成之後，把 BSL 改回 ReadWrite。唯讀期間，TTL 清理也會暫停。

### 第 74 頁｜分批還原應用，再逐層驗證

應用分三批還原。

第 1 批：drawio、filebrowser、flarum、planka、onlyoffice、peertube。它們各自獨立，DB 和 App 在同一個 namespace。
第 2 批：cloudbeaver，它跨 namespace 連第 1 批的 DB，所以要等第 1 批好了。
第 3 批：dr-demo，課程 lab。
永不還原：kube-system、velero、rook-ceph、cattle-*、etcd-backup，這些由各自的安裝程序重建。

腳本是 `restore-apps-in-order.sh`，後面接備份名稱，先 dry-run。每一批做完，用 `datadownloads | grep -v Completed` 檢查有沒有還沒完成的資料下載。

Velero 會先還原 Namespace 物件和它的 label，再還原 Pod，剛好避開 Cilium 那個「label 要比 Pod 先存在」的陷阱。

驗證分層：平台；資源與 baseline 比對；dr-demo 用 `check-data.sh`；flarum 等的 DB 用 cloudbeaver 查一筆災難前的資料；對外網址用 `curl --resolve`；最後由應用負責人驗收。

最後記錄實際 RTO，從宣告災難到業務驗收通過；以及實際 RPO，最後一份可用備份到災難的時間差。

### 第 75 頁｜為什麼不用 etcd snapshot 還原整座叢集

直覺上，etcd snapshot 就是整座叢集，為什麼叢集消失的時候不直接用它？因為放到新機器上會遇到這五個問題。

Node 物件：snapshot 裡是舊節點，新節點名稱或 IP 不同就對不上。PV：snapshot 裡的 PV 指向舊 Ceph 的 image ID，新 Ceph 上不存在。憑證：必須連 PKI 一起沿用，否則所有 token 和 kubeconfig 失效。加密金鑰：必須沿用舊的 `encryption-config.yaml`。基礎元件狀態：Cilium、Rook 的 CR 描述的是舊環境，舊的 OSD、舊的 IP。

所以結論：etcd snapshot 適合「同一批機器，只是 etcd 壞了」。叢集整個不見的時候，**乾淨重建加 Velero 還原應用**，才是可預期、可重複的流程。這也是單元 6 決策表最後一列的理由。

### 第 76 頁｜Velero Schedule：線上現況與建議

這張表逐欄比較線上的 `daily-full-backup` 和建議版本。

schedule 是 `0 1 * * *`，01:00 UTC，也就是台灣早上 9 點，不變。

excludedNamespaces：線上沒有設，建議排除 kube-system、kube-public、kube-node-lease、velero、rook-ceph。**排除 velero 就是修正問題 2。**

excludedResources：線上沒有設，建議排除 VolumeSnapshot、VolumeSnapshotContent、Event，這些都是還原沒有意義的暫時物件。

snapshotMoveData 是 true，不變，資料必須搬出叢集。TTL 720 小時，30 天，不變。`useOwnerReferencesInBackup` 是 false，不變，如果設成 true，刪 Schedule 會連帶刪掉所有備份。

最下面再提醒一次：這座叢集裝了 Rancher Fleet，`kubectl get schedules` 拿到的是 Fleet 的空清單。一律寫 `schedules.velero.io`，或用 `velero schedule get`。撰寫課程時就被誤導過一次。

### 第 77 頁｜TTL 與分級保留

上面這張表是分級保留的例子。`critical-6h`：每 6 小時、保留 7 天，給關鍵應用，RPO 6 小時。`daily-full-backup`：每天、保留 30 天，全叢集，RPO 24 小時。`weekly-full`：每週、保留 90 天，用在發現資料被慢慢改壞時回溯。`monthly-archive`：每月、保留 365 天，給稽核和法規。後兩個是練習題。

下面三個陷阱。

TTL 太短，加上問題太晚發現：所有備份都已經包含錯誤的資料。

備份停了，TTL 照常刪舊備份：停得夠久，連最後一份好的也會被刪。所以要監控「最新成功備份距今多久」。

手動刪除要用 `velero backup delete`。`kubectl delete backup` 只刪 CR，下次同步又會從 bucket 長回來。

TTL 到期時，Velero 會自動刪除 Backup CR、S3 上的備份檔，以及 kopia 裡不再被引用的資料。kopia 會去重，每日增量通常遠小於全量：dr-demo 的 PV 資料約 47.8MB，在 S3 上占用約 37MB。

### 第 78 頁｜Restore Test：唯一抓得到問題 2 的方法

上面這張表比較四種驗證方式能抓到什麼。

看 UI 或 `velero backup get`：只看 Phase 和 errors，問題 1、問題 2 都抓不到。
backup-check 每日：檢查沒產生、太舊、失敗，抓得到問題 1，抓不到問題 2。
自動 Restore Test 每週：驗證還原流程、PV 資料、應用資料，兩個都抓得到。
人工 DR 演練每季：驗證 runbook、人員、權限、RTO，兩個都抓得到。

下面是 restore-test 的三個設計原則。固定目的地加上 namespace 內的 Role：`dr-restore-test` 事先建好，Job 不需要叢集層級的權限。只刪自己還原的東西：用 `velero.io/restore-name` label 清除，不會誤刪。驗證資料，不是驗證狀態：直接重用單元 4 的 `check-data.sh`。

restore-test.sh 的流程：找出最新一份包含目標 namespace 的 Completed 備份，用 namespaceMapping 還原到 `dr-restore-test`，等 Deployment Ready，跑 `check-data.sh`。通過就清除這次還原的資源；失敗就保留現場供除錯。最後通知結果和耗時。

### 第 79 頁｜企業 DR Policy 至少要寫下這些

這張表是企業 DR Policy 最少要寫下的六項。

應用分級：Tier 1 是營收或對外服務，Tier 2 是內部重要系統，Tier 3 是可以重建的。RPO / RTO：例如 Tier 1 是 1 小時 / 4 小時，Tier 2 是 24 小時 / 1 天，Tier 3 是 7 天 / 盡力。備份方式：Tier 1 用 Velero 每小時加資料庫原生備份，Tier 2 用每日 Velero。保存與監控：叢集外 S3 加異地副本、每日 backup-check、沒收到通知時的處理方式。驗證：每週自動 Restore Test、每季人工演練、紀錄存查。角色：誰宣告災難、誰執行、誰驗收、誰對外溝通。

最下面這句話請帶回去：**RPO / RTO 不是技術人員自己決定的數字，而是業務方根據代價決定、IT 用演練證明。沒有演練過的 RTO，只是一個願望。**

【練習】請學員為自己公司的 3 個應用填寫這張表。Runbook 要放在叢集外、離線可取得；每次演練或事件後，更新 RPO、RTO 的實測值與 runbook。
